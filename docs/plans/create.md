# Agent HQ — Architecture Plan (v12, renamed 2026-10-24 from "dev-bridge", v11)

Agent HQ (formerly "dev-bridge") is a local web service at the headquarters of agent-managed
work: a conversational "project manager" agent (OpenClaw, via MCP) and development agents
(ZCode, first implementation behind a provider abstraction) meet here — plans, session
activity, events and agent-to-agent conversation. OpenClaw scopes and submits plans; the human
hands plans to ZCode sessions; Agent HQ tracks session activity and plan state so OpenClaw can
see the state of the work without doing any of it. It manages the work; it never replaces it.

The lifecycle, session tracking, event stream and MCP façade are not specific to development:
a plan can be research, operations or writing, and is tracked the same way. The name says so;
the body of this plan is unchanged by the rename except where identifiers appear.

This document is written to be implementable by a developer with no prior context. Where a
decision was made, it is stated once, explicitly, in this file. If something is not specified
here, do not invent a second subsystem — make the simplest choice consistent with what is
here, and record the choice in the Status Log.

## Stack

- C# / .NET 10 (installed: 10.0.113), ASP.NET Core Minimal API, Kestrel, bound to
  `127.0.0.1` only (never `*`)
- SQLite via Dapper (queries) + DbUp (migrations) for Agent HQ's own database
- SSE for push events; MCP façade via the official C# MCP SDK (streamable HTTP) for OpenClaw
- xUnit, Moq, `WebApplicationFactory`/TestServer, `Xunit.SkippableFact` for tests

## Reality on disk (verified 2026-10-24)

ZCode already maintains an authoritative internal index at `~/.zcode/cli/db/db.sqlite`
(WAL mode, safe for a second read-only connection):

- `session`: id, project_id (derived from cwd), title (from first input), directory,
  time_created/updated/archived/deleted, task_type, last_outcome
- `message`: per-session ordered messages (role: user/assistant) with monotonic `sequence`
- `part`: message content blocks typed `text`, `reasoning`, `tool`, `step-start`, `step-finish`,
  `timeline`, `compaction`, `file`, with `sequence`

`~/.zcode/cli/rollout/model-io-session_*.jsonl` are raw model I/O dumps that rotate — not a
reliable source of truth; we never read them.

We read ZCode's db **through the provider abstraction**, taking the main fields we need
(projects, sessions, messages, parts) as ZCode represents them. The coupling to a private
schema is quarantined inside the ZCode provider behind a schema guard (below).

Also verified: ZCode hooks receive `${CLAUDE_SESSION_ID}` as a template variable, and the
agent environment does NOT expose the session id. The session id that arrives via the hook
is the same id as `session.id` in the db — this is what makes hook attribution work.

### Schema guard (specifics)

At startup the provider opens the ZCode db read-only and reads its schema-version marker
(the `schema_migration` table's latest applied version; capture the exact query when building
the fixture in phase 1 and hard-code the tested version as a constant, e.g.
`TestedZCodeSchemaVersion = N`).

- Marker present and ≤ tested version → run normally.
- Marker > tested version → log a warning and run in **degraded mode**: serve what parses,
  but `GET /health` reports `provider: "schema-ahead"` and every provider call that hits an
  unexpected shape returns an error result rather than throwing.
- Marker/tables missing entirely → same degraded mode with `provider: "missing"`. The bridge
  starts and serves its own plan state regardless; only the session-mirror features degrade.

## Terminology

**Repository**, not project — ZCode's task list already says "projects" (projects live inside
repos), so we avoid the collision. A repository is a working tree root with a plans directory.
The provider maps its concept (ZCode `project_id`) onto repositories by root path
(`session.directory` gives us the path; a `project_id` maps to the root path most recently
seen among its sessions).

## Identity and naming (decided once, used everywhere)

The service is **Agent HQ** (2026-10-24, renamed from "dev-bridge"): one `AgentHQ` prefix for
projects, namespaces and types; lowercase-hyphen for everything a machine reads —
`agent-hq.service`, `AGENTHQ_*` environment variables, `~/.local/share/agent-hq`,
`scripts/agent-hq-deploy.sh`, the `AgentHQ.Api` binary. Prose says "Agent HQ".

- **Plan id**: a GUID, generated by Agent HQ. It is the identifier in every API path
  (`/plans/{id}`) and every DB reference.
- **Plan slug**: URL/filesystem-safe (`^[a-z0-9][a-z0-9-]*$`), unique *per repository*,
  derived from the plan name on submit (lowercase, spaces → `-`, strip the rest, suffix
  `-2`, `-3` on collision). The slug is the file name: `docs/plans/<slug>.md`.
- **Repository id**: the slug of the repository root path (absolute path, lowercased,
  `/` → `-`). API accepts either the id or the absolute root path wherever a repository is
  referenced.
- **`<file>` argument in `/plan` commands**: the bridge accepts a slug, a path relative to
  the repository root (`docs/plans/x.md`), or an absolute path — in that resolution order,
  resolved against the repository derived from the hook's `cwd`. If it resolves to zero or
  more than one plan, the hook ingest records an error event (`hook.rejected`, payload has
  the raw prompt and reason) and no transition happens.

### Provider abstraction (ZCode is impl #1)

```csharp
public interface IAgentProvider
{
    string Id { get; }                                  // "zcode"
    Task<IReadOnlyList<RepositoryInfo>> ListRepositoriesAsync();
    Task<IReadOnlyList<SessionInfo>> ListSessionsAsync(SessionQuery q);
    Task<SessionDetail> GetSessionAsync(string externalId);
    Task<SessionDelta> GetMessagesAsync(string externalId, SessionMessageQuery q); // cursor + filters
    ValueTask SubscribeAsync(Func<ProviderEvent, Task> onEvent, CancellationToken ct);
}
```

`SessionMessageQuery` carries `AfterSequence` and include/exclude flags for part types
(`reasoning`, `tool`, `step-*`). The provider maps ZCode's rows into our domain objects —
nothing ZCode-shaped crosses the boundary.

`RepositoryInfo` = `{ ExternalProjectId, RootPath, LastSeenAt }`. `SessionInfo` = `{ Id,
RootPath, Title, TaskType, LastOutcome, TimeCreated, TimeUpdated, Archived, Deleted }`.

## Change detection (event-driven, not polling)

1. FileSystemWatcher on the ZCode db directory watching `db.sqlite`, `-wal`, `-shm`
   change/renamed events.
2. Debounce ~500 ms, then read `PRAGMA data_version` on a **dedicated long-lived SQLite
   connection held open for the lifetime of the watcher** (data_version is per-connection:
   opening a fresh connection resets it and the check silently stops working — do not let a
   connection pool serve this). Skip the diff if unchanged.
3. Diff `session` rows above the last `time_updated` high-water mark → created/updated
   events. **Known assumption:** message/part writes bump `session.time_updated`. Verify this
   in phase 4 against a live session; if false, add a `max(part.sequence)` per-session
   secondary check inside the same debounced pass.
4. Safety net: startup full sync + one `data_version` check per minute (backstop for dropped
   inotify events, not the primary mechanism).

## Agent HQ data model (own SQLite, DbUp-migrated)

- `repositories` — id (path slug), root_path, provider, external_id, plans_dir (default
  `docs/plans`), is_default, first_seen_at
- `sessions` — mirror of provider metadata: provider, external_id, repository_id, title,
  task_type, last_outcome, external time_created/time_updated, first_user_message_excerpt,
  ingested_at. Messages are NOT mirrored (read-through with cursor).
- `plans` — id (GUID), slug, name, repository_id, file_path, status, priority (int, default 0,
  higher = sooner), is_blocked, blocked_reason, session_external_id nullable (the
  implementing session of record), implemented_by_session_id nullable (session that claimed
  `implemented` — this is what separation-of-duties compares against), content_hash, version,
  timestamps
- `plan_blocks` — plan_id, reason, resolution (nullable), blocked_at, unblocked_at, actor
- `plan_dependencies` — plan_id, requires_plan_id (cycle-checked on insert with a recursive
  CTE; a plan cannot depend on itself transitively; self-reference rejected outright)
- `lessons` — index over each repository's `docs/plans/lessons.md`: repository_id, entry_id
  (`L-<n>`), title, category, source_plan_id, content_hash, first_seen_at
- `plan_status_history` — plan_id, from_status, to_status, actor_type (`session` / `openclaw`
  / `andy`), actor_session_id nullable, command (the `/plan …` prompt or API route),
  git_head nullable, note (human-readable summary from the command's `<reason>`/evidence
  argument if present), at. **Narrative evidence (test output, commit lists, findings) is NOT
  stored here** — it lives in the plan file's Status Log, which the history row links to by
  plan + timestamp. Keep the DB row small and mechanical.
- `events` — autoincrement seq, type, payload JSON, at (SSE replay via Last-Event-ID)

## Plans

**Storage:** markdown inside each repository at `docs/plans/<slug>.md`. The bridge writes the
file on submit, indexes it, and watches the plan dirs — when anyone (usually ZCode) edits a
plan file, a hash change bumps version and emits `plan.updated`.

**Self-write suppression:** the bridge's own writes (submit, `PUT /content`) update
`content_hash` in the same transaction that writes the file. The watcher ignores a file
change whose resulting hash equals the indexed hash, and otherwise treats it as external.
This prevents duplicate events and spurious version bumps on bridge-initiated writes.

**Plan document convention** (defined in the guide, enforced softly): sections for Goal,
Context, Steps (markdown checkboxes — the progress source), Dependencies, Verification
Criteria (what a verifier works through), Documentation (docs are part of the deliverable,
written during implementation, not after), and a Status Log (append-only record of phase
claims and evidence). Section detection: a `## <Name>` heading; a section ends at the next
`## ` heading or EOF.

**Checkbox parsing (exact rule):** within the `## Steps` section only, count lines matching
`^[ \t]*[-*] \[[ xX]\]` (indented items included — they are sub-steps and count).
`progress = { checked, total }` over that set. Plans without a Steps section or without
checkboxes report `{ checked: 0, total: 0 }`.

**Dependencies:** `plan_dependencies` edges; enforcement is **soft**: transitioning to
`implementing` with unmet dependencies returns a warning (not a block) and the response names
the unmet plans. `GET /plans?ready=true` means: status is `in_review`, not blocked, not
deferred, and every dependency's status is `verified` or `done`. That query is how OpenClaw
herds.

**Priority:** a plain integer on each plan (default 0, higher = sooner). Lists default-sort by
priority desc then last-updated desc; OpenClaw and the human set it via `PATCH /plans/{id}`.
Deliberately just a number — an ordering signal for herding, nothing enforced.

**Lessons — the recursive improvement loop:** ZCode sessions are ephemeral; the system's
memory must live in the repository, not in the agents. Each repository keeps a lessons
knowledge base at `docs/plans/lessons.md` — append-style entries: a `### L-<n>: <title>`
heading, a category line (tests / concurrency / error-handling / …), an imperative lesson,
and the source plan. It lives inside the plans directory so the plan watcher already covers
it. The loop has three moments:

- **Capture** — on `verifying → fixing`, the `/plan fail` template requires the verifier to
  classify each failure: a foreseeable oversight becomes a drafted lesson entry; a genuinely
  novel problem yields none. The fixing session root-causes and refines the draft as part of
  `/plan implemented` (state-aware, fixing branch).
- **Consult** — every `/plan` work command (`start`, `review`, `implement`, `verify`)
  instructs the agent to read `docs/plans/lessons.md` before working, and `/plan implemented`
  evidence lists which lessons were accounted for. OpenClaw consults lessons (`list_lessons`)
  when drafting Verification Criteria, so past classes of oversight get caught at
  plan-authoring time, not just at verification time.
- **Distill** — AGENTS.md carries a short standing section pointing at the lessons KB and the
  `/plan` workflow (a shipped snippet, installed by the installer), so every fresh session
  knows both exist. Periodically — human or OpenClaw judgment — recurring lessons are
  promoted into AGENTS.md proper; always-on context earns its keep only for durable rules.
  Recurrence detection (same category failing across verifications) is a later addition, not v1.

The bridge watches `docs/plans/lessons.md` like plan files and indexes entries (parse:
`### L-<n>: <title>` headings; entry body runs to the next `### ` heading or EOF; category is
the first line starting `Category:`; source plan is the first line starting `Source:`).

**Lifecycle:** `submitted → refining → in_review → implementing → implemented → verifying →
verified → done`, with a dedicated rework loop `verifying → fixing → implemented` (failed
verification → fixes → back in the verification queue). `deferred` (postponed, with reason)
and `abandoned` from any state; `deferred → refining` re-activates. `fixing` keeps rework
legible from status alone and keeps the main line single-pass: `implementing` only ever exits
to `implemented`, and `verified` is only reachable from `verifying` — so there is never a
question of "implementing → verified or → implemented?".

**Blocked — an orthogonal flag, not a lifecycle state:** an agent that cannot proceed — during
implementing, verifying, anywhere — marks the plan blocked with `/plan block <file> <reason>`;
`/plan unblock <file>` clears it, optionally noting the resolution. The lifecycle status
never moves while blocked: the resume point after unblocking is implicit (it never left), and
the full history (`plan_status_history` plus `plan_blocks`) still tells the whole story.
`plan.blocked` / `plan.unblocked` events carry the reason, and `GET /plans?blocked=true` is
the needs-attention queue — a blocked plan is precisely the thing the man-in-the-middle wants
surfaced, and OpenClaw's primary herding trigger. Recurring block reasons are lesson
candidates, same as verification failures.

## Transitions: who moves what, and how we "know"

The bridge can never *know* work happened — it records **claims**: each transition carries an
actor, a mechanical record, and a timestamp, and the chain is auditable. Trust comes from two
rules:

1. **Separation of duties** — the session recorded in `implemented_by_session_id` may not be
   the session that claims `verified`. Soft-enforced: mismatch produces a warning in the
   response and a `separation_of_duties_warning: true` flag in the history row; the
   transition still happens.
2. **Evidence requirements** — forward claims must produce narrative evidence; see table.

### Mechanism: /plan commands + hook feed (solves intent AND attribution)

A ZCode slash-command pack ships with the bridge. Each command is a prompt template that
tells the agent what the phase means and how to do the work (full list in the Appendix). The
*transition itself* is recorded by the bridge via the **hook feed**: a `UserPromptSubmit`
hook POSTs `{session_id: "${CLAUDE_SESSION_ID}", prompt, cwd}` to
`POST /hooks/zcode/prompts`. The bridge:

1. Resolves the session (by session id against the provider; if the session is not yet in the
   mirror — race with the watcher — performs an immediate provider lookup rather than
   waiting).
2. Resolves the repository from `cwd` (longest registered root path that is a prefix of cwd).
3. Matches the prompt against `/^\/plan\s+(\w+)\s+(.+)$/` — subcommand, then argument.
4. Performs the transition with full attribution (actor = session id), snapshots
   `git rev-parse HEAD` in the repository root for `implementing`, `implemented`, and
   `verified` transitions (store in history row's `git_head`; repository not a git repo →
   null), and emits the corresponding SSE event.
5. Unrecognized or unresolvable → `hook.rejected` event, no state change.

If the plan has no `session_external_id` and the command is a work command (`start`,
`implement`), the bridge sets it and emits `plan.session_linked`.

**Evidence transport:** the hook feed carries prompts (intent + attribution) but not agent
output — so all agent-produced evidence flows through files the bridge already watches: the
plan's Status Log (phase claims, commits, test results, review findings, verification
reports) and `docs/plans/lessons.md`. The bridge does **not** parse Status Log prose into
transitions; it makes the file versioned and evented, and readers (OpenClaw, the human, the
next verifier) read the narrative there. The DB history stays mechanical (who, when, what
command, which commit). Plan-file edits ride along in the same commits as the work, making
plans historically useful artifacts in git.

Fallbacks, in order: hook feed down → auto-correlation (a session whose first message
mentions a plan file path links that session to the plan; linkage only, no transitions) and
manual `PATCH /plans/{id}/status` for transitions; MCP `update_plan_status` resolves the
calling session by newest-active-in-repository.

### ZCode-side installation (one command, idempotent)

`AgentHQ.Commands.ZCode` ships a script, `scripts/install-zcode-integration.sh` (also
exposed as `dotnet run --project AgentHQ.Api -- install-zcode`), that:

1. Copies the `/plan` command templates to `~/.zcode/commands/plan/<name>.md` (user scope —
   available in every project; overwrite if the installed file's first-line marker
   `<!-- dev-bridge v<N> -->` differs from ours, leave user-edited files alone and warn).
2. Registers the hook by merging into `~/.zcode/settings.json` under
   `hooks.UserPromptSubmit` a single entry running
   `curl -sf -X POST http://127.0.0.1:<port>/hooks/zcode/prompts -H 'Content-Type: application/json'
   -d '{"session_id":"${CLAUDE_SESSION_ID}","prompt":"$PROMPT","cwd":"$CWD"}' || true`
   (exact template-variable names confirmed against a live hook in phase 6 before shipping;
   `|| true` so a down bridge never blocks prompting). Merge is key-based and idempotent.
3. Appends the dev-bridge section to the managed repository's `AGENTS.md` if the marker
   `<!-- dev-bridge -->` is absent.

The installer is part of phase 6's deliverable and is tested by running it against a fake
`HOME` in the test suite.

### Transition table

| From → To | Trigger | Actor | Narrative evidence (lives in Status Log) |
|---|---|---|---|
| — → submitted | `POST /plans` | OpenClaw | plan content |
| submitted → refining | `/plan start <file>` | ZCode session | session link |
| refining → in_review | `/plan review <file>` | reviewer session | review findings |
| in_review → refining | `/plan sendback <file> <reason>` | reviewer session | concerns raised |
| in_review → implementing | `/plan implement <file>` | ZCode session | approval; dependency check (soft warning) |
| implementing → implemented | `/plan implemented <file>` | implementing session | summary, commits, test results; sets `implemented_by_session_id` |
| implemented → verifying | `/plan verify <file>` | verifier session or OpenClaw | verifier identity |
| verifying → verified | `/plan pass <file>` | verifier session or OpenClaw | report vs Verification Criteria |
| verifying → fixing | `/plan fail <file> <reason>` | verifier session or OpenClaw | failures found + lesson drafts |
| fixing → implemented | `/plan implemented <file>` (state-aware) | fixing session | what was fixed, commits, test results |
| verified → done | `/plan done <file>` or `PATCH /plans/{id}/status` | human or OpenClaw | — |
| any → deferred | `/plan defer <file> <reason>` | any | reason |
| deferred → refining | `/plan reactivate <file>` | any | — |
| any → abandoned | `/plan abandon <file> <reason>` | any | reason |

`/plan verify` is a **short-cut entry**: it accepts plans in `implementing`, `fixing`, or
`implemented`; if the plan is not already `implemented` it first records `→ implemented` and
then `→ verifying`, both attributed to the verifying session, so history plainly shows the
implementer never made the claim. Verdict commands (`/plan pass`, `/plan fail`) are the
agents' only way to close the loop — they are separate from `/plan verify` because the
verdict arrives *after* the verification work, possibly much later in the session.

`/plan implemented` is the trust gap the table makes explicit: it's a self-report. The command
template forces the agent to state what was done, list commits, and paste test results —
that evidence lands in the plan file's Status Log, and the mechanical claim lands in
`plan_status_history`, so a later verifier (and OpenClaw, via digest) audits it. If the agent
never reports, the plan sits in `implementing` with an idle session — which is exactly the
stuck-state signal OpenClaw herds on.

**Verification scheduling:** the bridge stays passive — it exposes
`GET /plans?status=implemented` as the verification queue. OpenClaw can itself be the judge
for criteria it can check from recorded evidence and session digests (it never implements, so
separation of duties holds), as a scheduled task; heavier verification rides Andy's existing
pattern of scheduled ZCode sessions (the "Daily 9 AM" / "Nightly 4:30" sessions already in
the db), which run `/plan verify` against the queue. OpenClaw can also trigger verification
reactively on `plan.status_changed → implemented` events. No bridge-side scheduler in v1.

## Session condensation (digest) — the OpenClaw reading model

Tiered reads keep OpenClaw's context overhead low (deterministic only — **no AI summarization
in the bridge**, agreed: risk of losing information; OpenClaw summarizes from digests itself):

- **L0 — `GET /sessions`**: metadata table (title, repository, updated, outcome, derived
  status: `active` = not archived/deleted and `time_updated` within 30 minutes; `idle` = not
  archived/deleted and older; `archived`/`deleted` pass through).
- **L1 — `GET /sessions/{id}/digest`**: deterministic condensation, markdown: header →
  user messages verbatim (rare, high-signal) → assistant `text` parts (tail-weighted) →
  state-changing tool calls as one-liners (`Edit docs/plans/x.md`, `Bash: git commit …`,
  test runs) → drop `reasoning`, `step-*`, `timeline`, `compaction`, raw tool output.
  `?budget=<chars>` (default 8000): first render the full digest; if over budget, drop the
  oldest assistant text parts first (keep all user messages and the last 20% of content
  verbatim) until within budget; append a `(… N earlier items elided …)` marker where
  content was dropped.
- **L2 — `GET /sessions/{id}/messages?after=<seq>&include=reasoning,tool`**: filtered delta.
- **L3 — raw parts**: debug only.

## Events, SSE, and catch-up

- `GET /events` — one SSE stream. Types: `session.created`, `session.updated`,
  `plan.created`, `plan.updated`, `plan.status_changed` (payload: `{from, to, actor, command,
  gitHead, plan summary}` — used for *every* status transition including deferred/abandoned),
  `plan.session_linked`, `plan.blocked`, `plan.unblocked`, `hook.rejected`.
- Event `id:` = bridge `events` seq; reconnect with `Last-Event-ID` (or `?lastEventId=`)
  replays missed rows from SQLite before streaming live.
- Heartbeat comment every 15 s; `retry:` hint; `?types=` filter.
- **Poll form for MCP-only consumers**: `GET /events?sinceSeq=<N>&types=…` returns the same
  rows as JSON — an OpenClaw that cannot hold an SSE connection stays current with one cheap
  cursor query per conversation turn instead of re-listing everything.
- Event payloads are self-describing (embedded plan/session summary + transition record).
- **Catch-up endpoints**: `GET /sessions?updatedSince=`, `GET /plans?status=` —
  snapshot-then-stream. The MCP guide teaches OpenClaw this pattern.

## API surface

All endpoints on `127.0.0.1` only. No auth in v1 (single-user machine); the hook endpoint
validates that `cwd` resolves under a registered repository and otherwise rejects.

## The OpenClaw side: being informed, accepting plans, reporting status

**Transport decision — MCP, not raw HTTP.** OpenClaw is a native MCP client (server
definitions live under `mcp.servers` in its config); MCP gives it tool discovery, typed
schemas, and descriptions with zero prompt-writing on its side. Direct API access would be
*thicker*, not thinner — endpoint knowledge would have to live in prompts and would drift.
The REST API remains for humans and debugging; the MCP façade is thin wrappers over the same
service handlers, so both stay in sync by construction.

**The thinness principle: state lives in the bridge.** All procedural knowledge — tool
contracts, the playbook, the operational picture — is carried by the bridge (tool
descriptions, `get_guide`, `get_overview`). The OpenClaw side reduces to three small
artifacts:

1. one `mcp.servers` entry registering the bridge;
2. a short section in the workspace `AGENTS.md` ("development is managed via dev-bridge;
   the tools are self-describing; orient with `get_overview`") — workspace files load every
   session, so this knowledge does not fade the way conversational prompts do;
3. a `HEARTBEAT.md` entry (or skill) running the scheduled PM loop below — each heartbeat
   wake starts a fresh context, so orientation is recomputed (`get_overview` → `sinceSeq`
   catch-up), never remembered.

Repeatable procedures beyond the loop (judging verification, drafting plans against lessons)
ship as a small SKILL.md pack in the workspace, loaded on demand. The rule that defeats
knowledge drift: **OpenClaw never remembers what it can re-derive in one cheap call**; its
own running notes go to workspace `MEMORY.md`, which persists across sessions.

What OpenClaw needs to operate effectively, mapped to its four jobs:

**1. Orient (one glance).** `get_overview` / `GET /overview` — repositories, plans grouped by
status (blocked ones with reasons), the verification queue, recently active sessions, and the
last event seq. One orienting call at the start of every conversation beats assembling five
lists; agents behave better when the picture is cheap.

**2. Stay informed (two modes).** SSE `GET /events` for any HTTP-capable consumer, and for
MCP-only operation the `get_events` tool / `GET /events?sinceSeq=` poll form — the guide
teaches the rhythm: `overview` first, then `sinceSeq` catch-up each turn (or SSE held open
where supported), never re-listing. All list tools take `updatedSince`.

**3. Accept plans.** `submit_plan` with the convention embedded in the tool description and
guide; the bridge soft-validates sections (warns when Verification Criteria or Documentation
are missing rather than rejecting). OpenClaw drafts against `list_lessons` so past oversight
classes are designed out at authoring time, and sets initial priority/dependencies.

**4. Read status and agent behavior.** Plan status, checkbox progress, and Status Log
evidence come from `list_plans` / `read_plan` and the self-describing events; agent behavior
comes from session digests (L0 list → L1 digest per session). No AI summarization in the
bridge — OpenClaw condenses from digests into its own notes.

**Action repertoire** (the guide states it explicitly; all recorded with actor `openclaw`):
submit plans; send a plan back to refining after a needs-author review; set priority and
dependencies (herding); judge verification for criteria checkable from evidence and digests
(scheduled); close `verified → done`; surface blocked plans to Andy with the recorded reason
and, where it can help, append the missing answer to the plan content itself. What OpenClaw
never does: touch code, or verify a plan it implemented itself (it never implements).

**Scheduled PM loop** (rides OpenClaw's own scheduling, like Andy's scheduled ZCode
sessions): `get_overview` → judge the `implemented` queue where criteria permit → check
`blocked=true` and blocked reasons → report a short state-of-development summary to Andy.
The bridge stays passive throughout; the loop is prompts and tools, not bridge machinery.

**How the guidance is delivered** (layered): server `instructions` on MCP initialize (mission
+ workflow, ~200 words); per-tool descriptions carrying contract and etiquette (pass
`updatedSince`, use `ready=true`, herd on stuck states); `get_guide` tool +
`dev-bridge://guide` MCP resource carrying the full playbook (plan convention, lifecycle
semantics and who moves what, digest usage, catch-up rhythm, separation of duties, lesson
consultation); and self-describing event payloads.

## Run model

- **Development:** run from the terminal (`dotnet run`).
- **Steady state:** systemd user service — `Restart=on-failure`, `RestartSec=1`, journals
  logs; unit file ships in-repo (`ops/dev-bridge.service`); single-file publish.
  Port choice: fixed default `5317` (configurable via `AGENTHQ_PORT` env / config file) so
  the hook URL is stable.

## Logging (mirrors NASTV)

Serilog (as NASTV): console sink for terminal runs + rolling file sink,
`rollingInterval: Day`, `retainedFileCountLimit: 10`, size-capped files under
`~/.local/share/dev-bridge/logs/`. Structured, with per-subsystem properties
(watcher, provider, plans, hooks, mcp) so logs are filterable. Hook-feed ingests and state
transitions log at information; FS watcher detail at debug.

## Testing strategy (NASTV conventions)

- **Unit (xUnit + Moq):** state machine transition rules (legal/illegal, short-cut entry,
  verdict commands, separation-of-duties warning), digest projection and part filtering,
  checkbox/lesson parsing, `/plan` command parsing from hook-feed prompts, high-water diff
  logic, slug generation and collision suffixing.
- **Provider fixture:** a checked-in DDL snapshot of the real ZCode schema (captured once via
  `sqlite3 ~/.zcode/cli/db/db.sqlite .schema` during phase 1, committed as a `.sql` fixture —
  not re-captured at build time, so tests are deterministic) seeded with
  sessions/messages/parts. The provider is tested against a real-shaped db, not mocked rows;
  the schema guard is tested against bumped schema versions.
- **Integration (WebApplicationFactory / TestServer):** full API in memory with temp
  directories — synthetic zcode db, a fake repository with `docs/plans/`, real
  FileSystemWatchers (tests trigger them by writing files, with short debounce settings and
  time-boxed polling assertions instead of sleeps). Asserts mirrors, events, SSE streams,
  replay, and self-write suppression (a `PUT /content` must NOT produce `plan.updated`).
- **Installer tests:** run the installer against a fake `HOME` twice; assert idempotent
  (second run changes nothing) and that settings.json merge preserves unrelated keys.
- **E2E simulation — the whole loop, no live agents:** the harness plays every actor:
  1. write to the synthetic zcode db → assert `session.updated` reaches an SSE client;
  2. `POST /hooks/zcode/prompts` with `/plan start docs/plans/x.md` + session id → assert
     transition with attribution and `plan.session_linked`;
  3. write plan-file edits (Status Log entries, checkbox ticks) → assert version bump,
     progress recompute, `plan.updated`;
  4. run `/plan implemented` → `/plan verify` → `/plan pass` (and a second scenario
     `/plan fail` → `/plan implemented` → `/plan verify` → `/plan pass`) through the hook
     feed → assert the full chain, the fixing loop, and the short-cut entry;
  5. simulate OpenClaw by calling MCP tools through the C# SDK's client against our server
     (TestServer transport): `get_overview`, `get_events(sinceSeq)`, `submit_plan`,
     `update_plan_status` — asserting the PM loop reads exactly what the events carried;
  6. reconnect the SSE client with `Last-Event-ID` → assert gap replay.
- **Live smoke (env-gated `Xunit.SkippableFact`):** read-only against the real
  `~/.zcode/cli/db` — schema guard passes, real sessions list, a real digest renders, and
  the `time_updated`-bumps-on-message-write assumption is asserted true. Skipped unless
  `AGENTHQ_LIVE=1`.

## NuGet

Not needed in v1 — dev-bridge is a self-contained service; everything comes from nuget.org.
`nuget.config` mirrors NASTV's (clear + nuget.org + the private benow BaGetter feed,
anonymous pull) so that if the provider abstraction or domain model ever gains a second
consumer, tag-driven publishing to the feed follows the established conversation-repo
pattern with no setup work. dev-bridge produces packages only if that day comes.

## Deployment (CI/CD)

Same machine, so it is essentially a script — but it rides GitHub Actions on the local
self-hosted runner exactly as NASTV does, simplified to a single target:

- New GitHub repo; workflow on push to `main` (paths-ignore docs/markdown, as NASTV),
  `concurrency: group=deploy` to prevent overlap, `runs-on: [self-hosted, dev-bridge]`
  (label the local runner accordingly).
- Jobs: `build-and-test` (dotnet build + full test suite — the phase gate for main) →
  `publish` (single-file binary) → `deploy` running `scripts/dev-bridge-deploy.sh`.
- `scripts/dev-bridge-deploy.sh` (modeled on NASTV's nastv-deploy.sh, local-only v1):
  health-drain → stop systemd user service → rsync binary → start → `curl /health` check
  with rollback to the previous binary on failure. Quick restart turnaround is the
  requirement; the script does stop-copy-start, well under a second of downtime.
- `workflow_dispatch` for manual runs; the workflow file stays in-repo under
  `.github/workflows/deploy.yml` mirroring NASTV's shape.

## Documentation and phase gating

Each build-order phase ends with its tests green **and** its docs written (README section,
ops notes) before the next phase starts — the gate is the test suite, run per phase. The
final E2E simulation test is the acceptance gate for the whole build. Dogfooding note:
once the bridge runs, this plan (`docs/plans/create.md`) becomes plan #1 it manages, and
dev-bridge's own further development flows through its own lifecycle.

## Appendix: /plan command prompts (v1)

Each command is a ZCode slash-command prompt template. The hook feed records the transition
and emits the corresponding SSE event; agent evidence flows via the plan file's Status Log
and `docs/plans/lessons.md`. Reviewer/verifier commands must run in a *different session*
than the one that produced the work.

**`/plan start <file>`** (submitted → refining) — Take ownership of refining this plan to
implementable quality. Read AGENTS.md, `docs/plans/lessons.md`, and the full plan; ground it
in the actual codebase. Fill gaps, sharpen steps, add missing context, ensure Steps are
checkboxes and Verification Criteria are concrete and testable. You are refining, not
implementing — no code changes yet.

**`/plan review <file>`** (refining → in_review; different session than `/plan start`) —
Review this plan for gaps, inconsistencies, ambiguities, or anything else that would
negatively impact successful implementation by a junior developer. List your findings
explicitly and append them to the Status Log. Then apply your suggestions and rewrite the
plan for that junior developer — assume the implementer has no context beyond the plan and
the repository. Check the plan against every relevant lesson. Conclude with a verdict:
approved (ready for `/plan implement`), or needs-author (the human or OpenClaw runs
`/plan sendback`).

**`/plan sendback <file> <reason>`** (in_review → refining; reviewer) — Append the review's
concerns to the Status Log so the refiner addresses each one explicitly.

**`/plan implement <file>`** (in_review → implementing) — Execute the plan exactly. Read the
plan, AGENTS.md, and `docs/plans/lessons.md`; account for each relevant lesson in your work.
Implement step by step, ticking Steps checkboxes as you complete them; record any deviation
in the Status Log. Documentation is part of the deliverable: write/update it as the plan's
Documentation section specifies, alongside the code. Write and run the tests the plan calls
for. When finished, run `/plan implemented` — do not claim completion inside this command.

**`/plan implemented <file>`** (implementing → implemented; in `fixing`, fixes complete →
implemented) — Claim completion with evidence. Append to the Status Log: a summary of what
was implemented, commit hashes and subjects, tests run with results, documentation updated,
lessons consulted and how each was accounted for, and deviations from the plan. If you are in
the `fixing` phase: root-cause the verification failures, state the fix, and refine the
drafted lesson if it misses the nuance. Be precise — a different session will check every
claim against the Verification Criteria; overclaiming is the failure mode this evidence
exists to catch. Do not verify your own work.

**`/plan verify <file>`** (implemented → verifying; accepts `implementing`/`fixing` via the
short-cut — the bridge records the intermediate `→ implemented` attributed to you; different
session than `/plan implemented`, or OpenClaw as judge) — Adversarial verification, not
re-implementation. Read the Verification Criteria, the Status Log evidence, and the lessons.
Work through each criterion: run the tests and commands yourself; inspect the recorded
commits' diffs. Then run `/plan pass` or `/plan fail` — this command only enters verification;
it never moves the plan out of `verifying` itself.

**`/plan pass <file>`** (verifying → verified) — Append a verification report to the Status
Log: each criterion ✓/✗ and how it was checked. All criteria must pass to run this.

**`/plan fail <file> <reason>`** (verifying → fixing) — Append precise, reproducible
failures to the Status Log; classify each — foreseeable oversight → draft a lesson entry in
`docs/plans/lessons.md`; genuinely novel → note only. The next `/plan implemented` in the
fixing phase completes the loop.

**`/plan block <file> <reason>`** (set blocked flag) — State what is blocking you, what you
need to proceed, and what you have already tried. Append a Status Log note specific enough
for the human or OpenClaw to act on.

**`/plan unblock <file>`** (clear blocked flag) — Note the resolution in the Status Log
(what unblocked it), then resume the stalled work from where it stopped.

**`/plan defer <file> <reason>`** (any → deferred) — Record why it is postponed and what
would make it worth reviving. No further work now.

**`/plan reactivate <file>`** (deferred → refining) — Re-read the deferral reason; note in
the Status Log what changed to justify revival.

**`/plan done <file>`** (verified → done; human or OpenClaw) — Close the plan out.

**`/plan abandon <file> <reason>`** (any → abandoned) — Record why: superseded, no longer
needed, or wrong approach. History is preserved; the plan file stays.

### 2026-10-24 — deployment (systemd user service + CI)

Requested: easy start/stop, deploy as the code changes, resources copied to the deployment
location, restart when required; GitHub Actions "later", once there is a repository. Decisions:

1. **No container, no packaging step.** One self-contained single-file publish (102 MB, runs
   with no .NET on the target) plus the assets it reads from its own directory — `wwwroot/`
   and `Commands/` — which are already `CopyToPublishDirectory` assets of `AgentHQ.Api`, so
   the old workflow's extra `cp -r Commands` step (which landed in `artifacts/Commands`, not
   next to the binary) is gone.
2. **Releases as directories, `current` as the switch.** The script switched to
   `releases/<utc>-<sha>/` + `current` symlink after testing: the old copy-in-place design
   overlapped a stop with `rsync` over the running binary and had no notion of "the version
   that was running". Rolls back by switching the symlink back after the health deadline
   (60 s; a cold start takes 13–20 s because Kestrel opens only after the first ZCode sync).
   Verified with a deliberately crashing release: live release restored, exit 1, journal shown.
3. **Bugs found while doing it:** the workflow's deploy step invoked the script with no
   arguments while the script only deployed from `STAGE_DIR` (so CI would have failed); the
   the pipeline had renamed the binary away from the name the unit's `ExecStart` expected —
   the unit runs `current/AgentHQ.Api` (then still `DevBridge.Api`) and the script normalises
   any other single binary in a staged pile.
   `dev-run.sh` was not executable.
4. **Start/stop semantics.** `Restart=always` (a crash returns in ~2 s; verified with
   `kill -9`), `systemctl stop` still stops it, and `loginctl enable-linger` so a user unit
   survives logout/reboot — otherwise it silently dies with the session. `install` does that
   and enables the unit at boot; `start`/`restart` wait for health instead of failing on the
   first probe. `check` compares the running process's executable with `current`, so a deploy
   that dies after its health check cannot be reported as healthy.
5. **Log noise.** The service's journal was full of per-request ASP.NET lines. Framework log
   level is now `Warning` by default via `AGENTHQ_LOG_ASPNET` (Serilog override; the
   `Logging__LogLevel` env var would not have reached it). Subsystem logs are unchanged.
6. **CI, gated.** `deploy.yml` runs build+test → publish → the same deploy script (`STAGE_DIR`)
   → `check`, on the self-hosted runner. Jobs are gated on repo variable `RUNNER_ENABLED`
   because a job with a label no runner carries queues indefinitely. One-time setup once the
   repository exists: create it on GitHub, run the Actions runner with labels from
   `RUNNER_LABELS` (default `["self-hosted"]`), set `RUNNER_ENABLED=true`, and optionally add a
   `production` environment approval for the deploy job if the repo becomes public.
